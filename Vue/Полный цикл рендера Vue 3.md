### 1. Создание компонента

1. При монтировании Vue создает объект`ComponentInternalInstance`, он хранит:
`props`, `setupState`, `slots`, ссылка на родителя, список дочерних компонентов, последнее дерево Virtual DOM (`subTree`) и функция обновления (`update`).

2. Затем выполняется `setup()`. Все `reactive()`, `ref()` и `computed()` становятся частью реактивной системы.

3. Если шаблон не был заранее скомпилирован, он компилируется в функцию `render()`. При использовании SFC через Vite это обычно происходит еще на этапе сборки.
### 2. Создание Render Effect

После этого Vue создает `ReactiveEffect`, для компонента этот эффект становится **Render Effect** — главный механизм обновления компонента. Каждый его запуск означает полный цикл построения нового Virtual DOM
### 3. Первый рендер

Перед запуском Render Effect делает его текущим активным эффектом (`activeEffect`).

Во время выполнения `render()` происходит чтение реактивных данных. Любое обращение к `reactive` или `ref` проходит через Proxy, который вызывает `track()` - добавляет текущий Render Effect в структуру зависимостей (`targetMap`), где каждому объекту и каждому его свойству соответствует набор их эффектов

После окончания рендера активный эффект сбрасывается. Теперь Vue знает, какие именно компоненты используют каждое реактивное значение.
### 4. Построение Virtual DOM

Функция `render()` возвращает дерево `VNode`. Каждый `VNode` — это обычный JavaScript-объект, он сохраняется в `instance.subTree` и передается в `patch()`- он создает реальные DOM-узлы.
### 5. Изменение реактивных данных

Когда изменяется `reactive` или `ref`, Proxy вызывает `trigger()`. Эта функция обращается к `targetMap`, находит все эффекты, подписанные на изменившееся свойство, и начинает их обработку.

Важно, что поиск происходит не среди компонентов, а среди зависимостей конкретного реактивного свойства. Поэтому Vue не нужно обходить дерево компонентов, чтобы понять, кого необходимо обновить.
### 6. Scheduler

`trigger()` практически никогда не запускает Render Effect напрямую. Вместо этого вызывается `scheduler`, переданный при создании эффекта.

Scheduler помещает эффект в очередь обновлений (`Job Queue`). Если один и тот же эффект уже находится в очереди, повторно он не добавляется. Благодаря этому несколько последовательных изменений состояния приводят только к одному обновлению компонента.

Очередь выполняется в следующем microtask через `Promise.resolve()`, поэтому все синхронные изменения состояния успевают объединиться в один цикл обновления.

### 7. Flush очереди

После завершения текущего стека вызовов запускается `flushJobs()`.

Перед выполнением очередь сортируется, чтобы родительские компоненты обновлялись раньше дочерних. Если во время обновления появляются новые задачи, они также добавляются в очередь и будут выполнены в этом же цикле, пока очередь полностью не опустеет.
### 8. Повторный Render Effect

Scheduler вызывает `effect.run()`, после чего Render Effect снова становится активным.

Выполняется `render()`, который полностью строит новое дерево `VNode`. Vue не изменяет старое дерево — оно остается сохраненным в `instance.subTree`, а каждый рендер создает новую структуру Virtual DOM.

Во время повторного рендера снова вызывается `track()`, поэтому зависимости автоматически пересобираются. Если компонент перестал использовать какое-либо реактивное свойство, связь будет удалена, а если начал использовать новое — зарегистрирована.
### 9. Оптимизации компилятора

Главное отличие Vue от React заключается в том, что Vue знает структуру шаблона еще во время компиляции.

Компилятор выполняет **Static Hoisting**, вынося полностью статические узлы за пределы функции `render()`, поэтому они создаются только один раз и никогда больше не участвуют в обновлениях.

Затем добавляются **Patch Flags** — битовые маски, сообщающие `patch()`, какие именно части конкретного узла могут изменяться. Если известно, что изменяется только текст, Vue даже не проверяет `class`, `style` или остальные `props`.

Дополнительно строится **Block Tree**. Для каждого блока шаблона сохраняется список только динамических потомков. Во время обновления `patch()` проходит именно по этому списку, а не по всему дереву Virtual DOM.
### 10. Patch

После получения нового дерева начинается работа `patch(oldVNode, newVNode)`.

Функция сначала сравнивает типы узлов. Если тип изменился, старый DOM-элемент полностью удаляется и создается новый.

Если тип совпадает, начинается специализированное обновление. Для элементов сравниваются `props`, текст, события и дочерние узлы. Для списков используется алгоритм сравнения по `key`, позволяющий переиспользовать существующие DOM-элементы и минимизировать их перемещение.

После завершения обновления новое дерево сохраняется как `instance.subTree` и становится эталоном для следующего цикла.
