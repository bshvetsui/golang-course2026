## Аллокация памяти runtime.mallocgc
mallocgc - функция в рантайме которая распределяет данные по этим хранилищам:

1. **mcache** — локальный кэш у каждого `P`.
	   1. Здесь нет блокировок потому что доступ только у хозяина.
	   2. 95–99% аллокаций заканчиваются здесь.
	   3. Хранит по одному активному **span** каждого **size class** для быстрого выделения памяти без блокировок.
2. **mcentral** — общий запас **span**'ов по **size class**'ам.
	   1. Если у **mcache** закончилась память, он идет сюда.
	   2. Хранит свободные **span** каждого **size class** и пополняет ими **mcache**, когда активный **span** заканчивается.
3. **mheap** — главный менеджер памяти Go Runtime.
	   1. Управляет всеми страницами памяти, которые процесс получил у ОС.
	   2. Хранит память страницами по 8 КБ, а не отдельными объектами.
	   3. **Span** в его случае — это непрерывный участок из нескольких страниц.
	   4. Почти никогда не отдает память по одной странице, а выделяет ее **span**'ами.
4. **mmap()** - syscall для выделения диапазонов виртуальной памяти. Последняя точка, сюда практически никогда не ходят. 

 **Size class** — категория размера объекта (например: 16 B, 32 B, 64 B, 128 B...). Все объекты похожего размера попадают в один класс.
 **Span** — непрерывный участок памяти, выделенный под объекты **одного** size class.

## Белый → Серый → Черный

1. GC находит корневые объекты (стеки горутин, глобальные переменные) и красит их в **серый**.
2. Берет **серый** объект и просматривает все его ссылки:
   - найденные **белые** объекты делает **серыми**;
   - сам объект становится **черным**.
3. Повторяет процесс, пока **серых** объектов не останется.
4. Все оставшиеся **белые** объекты считаются мусором и освобождаются.
# Фазы работы Go Garbage Collector
**GOGC** - как часто запускается GC. **GOGC=100**, меньше - чаще, больше - реже 

1. **Mark Setup (STW)** — короткая остановка мира.
	   1. Включается **write barrier**.
	   2. Подготавливаются GC workers.
	   3. Все горутины доводятся до **safe point**.
	   4. Корневые объекты (стеки горутин, глобальные переменные) становятся начальными серыми объектами.
2. **Concurrent Mark** — основная фаза маркировки.
	   1. Программа продолжает работать.
	   2. GC workers обходят граф объектов по схеме **Белый → Серый → Черный**.
	   3. Новые объекты и изменения ссылок отслеживаются с помощью **write barrier**.
	   4. На GC выделяется примерно 25% CPU

3. **Mark Assist** — помощь сборщику мусора.
	   1. Если программа выделяет память быстрее, чем GC успевает маркировать объекты, выделяющая память горутина сама выполняет часть работы по маркировке.

4. **Mark Termination (STW)** — завершение маркировки.
	   1. Мир снова ненадолго останавливается.
	   2. Доделываются оставшиеся задачи маркировки.
	   3. Проверяется, что серых объектов больше не осталось.
	   4. Все живые объекты окончательно становятся черными.
	   5. Подготавливается переход к очистке памяти (**Sweep**).

5. **Concurrent Sweep** — очистка памяти.
	   1. Белые объекты освобождаются.
	   2. Освобожденная память возвращается в **mcache**, **mcentral** и **mheap**.
	   3. Программа продолжает работать параллельно с очисткой.
## Изменения нового GC Green Tea
1. Изменения касаются **mheap** и того как он работает в **Concurrent Mark** фазе, исправляет проблему частых write barrier
2. Раньше GC прыгал по страницам в поиске одного объекта, теперь быстрее - сканируется вся страница и объекты на помечаются двумя битами (bitmap) типа: 
	1.  00 — нет указателя
	2. 01 — указатель
	3. 10 — начало объекта
	4. 11 — специальные данные
3. Это связанно с переходом CPU на AVX инструкции, которые способны обрабатывать такие bitmap'ы сразу пачками
