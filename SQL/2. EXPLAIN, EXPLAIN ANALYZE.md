`EXPLAIN` — показывает **план выполнения**, запрос не выполняет.  
`EXPLAIN ANALYZE` — **реально выполняет запрос** и показывает фактическое время/строки.
```sql
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'a@mail.com';
```
Пример вывода:
```text
Seq Scan on users
(cost=0.00..2185.00 rows=1 width=64)
(actual time=0.03..14.52 rows=1 loops=1)
Filter: (email = 'a@mail.com')
Rows Removed by Filter: 99999

Planning Time: 0.12 ms
Execution Time: 14.55 ms
```
## Основные поля
1. `Seq Scan` — PostgreSQL читает таблицу целиком.
2. `Index Scan` — ищет через индекс, затем читает строку таблицы.
3. `Index Only Scan` — получает данные прямо из индекса.
4. `cost=0..2185` — **оценочная стоимость** планировщика, не миллисекунды. `start..total`. <100 - быстро, 100-1000 норм, >1000 много
5. `rows=1` — сколько строк PostgreSQL **ожидает** получить.
6. `width=64` — ожидаемый средний размер строки в байтах.
7. `actual time=0.03..14.52` — реальное время: первая строка → завершение узла.
8. `actual rows=1` — сколько строк реально вернулось.
9. `loops=1` — сколько раз выполнялся узел.
10. `Filter` — условие применялось после получения строк.
11. `Rows Removed by Filter` — сколько строк прочитали и выбросили.
12. `Index Cond` — условие использовалось непосредственно для поиска по индексу.
13. `Planning Time` — время построения плана.
14. `Execution Time` — полное время выполнения.
## Что искать
```text
Seq Scan
Rows Removed by Filter: 999999
```
Если нужна 1 строка, а читается миллион → вероятно нужен индекс.
```text
rows=10
actual rows=500000
```
Оценка сильно ошиблась → проверить статистику:
```sql
ANALYZE users;
```

```text
loops=100000
```
Узел запускается 100 000 раз → даже быстрый узел может тормозить запрос.

После индекса:
```sql
CREATE INDEX idx_users_email ON users(email);
```
План может стать:
```text
Index Scan using idx_users_email on users
Index Cond: (email = 'a@mail.com')
Execution Time: 0.05 ms
```
## Как анализировать
1. Смотри `Execution Time`.
2. Ищи дорогие `Seq Scan`.
3. Смотри `Rows Removed by Filter`.
4. Сравнивай `rows` ↔ `actual rows`.
5. Проверяй большие `loops`.
6. Проверяй, используется ли `Index Cond`.

Для продвинутого анализа:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```
`BUFFERS` — показывает, сколько страниц данных пришлось читать из памяти/диска.

⚠️ `EXPLAIN ANALYZE UPDATE/DELETE/INSERT` **реально изменяет данные**.
