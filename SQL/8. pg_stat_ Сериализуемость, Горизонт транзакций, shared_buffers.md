`pg_stat_*` — это системные **view PostgreSQL со статистикой работы БД**. Через них обычно мониторят нагрузку, запросы, таблицы, индексы и подключения.

1. `pg_stat_activity` — **что сейчас происходит в БД**: подключения, активные запросы, сколько выполняются, кто ждёт блокировку.
2. `pg_stat_database` — статистика **по всей БД**: число транзакций, rollback, чтения с диска/из cache, deadlock'и.
3. `pg_stat_user_tables` — статистика **по таблицам**: `SELECT/INSERT/UPDATE/DELETE`, количество live/dead rows, когда был `VACUUM/ANALYZE`.
4. `pg_stat_user_indexes` — статистика **использования индексов**. Можно найти индексы, которыми почти не пользуются.
5. `pg_stat_bgwriter` — статистика записи dirty pages/checkpoint'ов.
6. `pg_stat_replication` — состояние **репликации**, подключённые replicas и lag.
7. `pg_stat_wal` — статистика генерации WAL.
8. `pg_stat_statements` — **самые важные запросы для performance debugging**: сколько раз выполнялся запрос, среднее/суммарное время и т. д. Это extension, его нужно отдельно включить.
### Сериализуемость и линеаризуемость
1. **Serializability** — параллельные транзакции дают результат, как будто выполнялись **по очереди**. В PostgreSQL это `SERIALIZABLE`; конфликтующую транзакцию могут отменить и потребовать retry.
2. **Linearizability** — ещё строже: операции выглядят последовательными **и соблюдают реальное время**. Если запись уже завершилась, следующий read обязан её видеть.
3. Коротко: **Serializability = порядок транзакций**, **Linearizability = порядок + реальное время**.
### 2. Горизонт транзакций
1. PostgreSQL использует MVCC и `XID`, чтобы понимать, какие версии строк видны транзакции.
2. **Transaction horizon** — граница старых транзакций: версии строк старше неё уже не могут понадобиться активным транзакциям и могут быть очищены `VACUUM`.
3. Долгая транзакция держит горизонт далеко назад → `VACUUM` не может удалить старые версии → растёт `bloat`.
4. Поэтому опасны долгие `idle in transaction`.
### 3. `shared_buffers`
1. `shared_buffers` — RAM-кеш PostgreSQL для страниц **таблиц и индексов**.
2. Есть страница в кеше → читаем из RAM; нет → читаем с диска/OS cache и кладём в `shared_buffers`.
3. `UPDATE` меняет страницу в памяти → она становится `dirty` → позже записывается на диск.
4. Для отдельного PostgreSQL-сервера типичная стартовая настройка — около **25% RAM**
