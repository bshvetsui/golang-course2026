**Backup** — копия данных PostgreSQL для восстановления данных. **Replica ≠ backup**: реплика повторяет изменения **primary (основной БД)**, поэтому случайный `DROP TABLE` **(удаление таблицы)** тоже попадёт на неё.
## Виды backup

1. **Logical backup** — PostgreSQL выгружает структуру и данные в логическом виде. Инструменты: `pg_dump` — одна БД, `pg_dumpall` — все БД + глобальные объекты. Пример: `pg_dump -Fc mydb > backup.dump`, восстановление: `pg_restore -d mydb backup.dump`. Можно бэкапить отдельные объекты: `-t users` — таблица, `-n public` — schema, `--schema-only` — только структура, `--data-only` — только данные. Плюсы: можно восстановить отдельную таблицу/schema, удобно переносить между серверами и версиями PostgreSQL. 
   Минус: на больших БД backup/restore медленный.
2. **Physical backup** — копирование файлов PostgreSQL (`PGDATA`). Стандартный инструмент: `pg_basebackup`. Пример: `pg_basebackup -h postgres -D /backup/db -Fp -Xs`. Используется для больших БД, replica, Disaster Recovery и PITR. Плюс — быстрое восстановление всей БД, минус — неудобно восстанавливать отдельные таблицы.
3. **Full backup** — сохраняются все данные.
4. **Incremental backup** — сохраняются изменения после предыдущего backup.
5. **Differential backup** — сохраняются изменения после последнего full backup.

Для production backup обычно используют `pgBackRest`, `Barman`, `WAL-G`. (утилиты для бекапов)

## WAL и PITR
**WAL (Write-Ahead Log)** — журнал изменений PostgreSQL. Перед изменением файлов таблиц PostgreSQL сначала записывает операцию в WAL. WAL нужен для crash recovery, replication и PITR.  
**PITR (Point-In-Time Recovery)** — восстановление БД на конкретный момент времени. Например: `02:00 backup → WAL → WAL → 10:37`, затем в `10:38` сделали `DROP TABLE users` — можно восстановиться на состояние до удаления. Для PITR нужны physical/base backup и все WAL после него. Обычно WAL постоянно архивируются во внешнее хранилище, например S3.

## pg_dump
Обычный SQL dump:  
`pg_dump mydb > backup.sql`  
Восстановление:  
`psql mydb < backup.sql`  
Custom format:  
`pg_dump -Fc mydb > backup.dump`  
Восстановление:  
`pg_restore -d mydb backup.dump`  
Custom format удобнее: позволяет выбирать объекты и делать параллельный restore.

`pg_dump` делает **consistent snapshot** — приложение может продолжать писать в БД, а dump получает согласованное состояние на определённый момент времени. Обычно останавливать backend не нужно.

## RPO / RTO
1. **RPO (Recovery Point Objective)** — сколько данных допустимо потерять. `RPO = 5 min` → максимум потеряем последние 5 минут.
2. **RTO (Recovery Time Objective)** — сколько времени допустимо восстанавливать сервис. `RTO = 30 min` → PostgreSQL должен вернуться в работу максимум за 30 минут.

Обычно схема такая: `PostgreSQL → backup tool → S3/Object Storage`.
1. Периодический full/physical backup.
2. Постоянное архивирование WAL.
3. Хранение backup вне PostgreSQL-сервера.
4. Retention policy — сколько старых backup хранить.
5. Шифрование backup.
6. Мониторинг успешности backup.
7. Регулярная проверка restore.

Backup считается рабочим только если из него реально проверяли восстановление.
