**ACID** — четыре свойства, гарантирующие надёжность транзакций в реляционных СУБД.
- **Atomicity (Атомарность)** — Если хоть одна операция внутри транзакции завершилась ошибкой, откатываются все изменения
- **Consistency (Согласованность)** — транзакция переводит базу из одного валидного состояния в другое, она не должна привести к несогласованности данных.
- **Isolation (Изоляция)** — параллельные транзакции не мешают друг другу. Результат работы нескольких транзакций такой же, как если бы они выполнялись последовательно
- **Durability (Долговечность)** — если система подтвердила COMMIT, изменения сохранятся даже при сбое. Обеспечивается через WAL
## Как достигается ACID

- **Atomicity** — Undo log хранит старые значения, при ошибке выполняется откат
- **Consistency** — Constraints (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK), триггеры, логика приложения
- **Isolation** — блокировки или MVCC. СУБД гарантирует constraints, остальное — ответственность приложения
- **Durability** — WAL. Изменения сначала пишутся в лог, потом в данные, нужно просто архивировать этот лог и где то хранить, например в aws
## Atomicity — Undo Log
При изменении данных СУБД сохраняет старые значения в undo log. Если транзакция откатывается — восстанавливает из лога.
## Isolation — блокировки и MVCC

- **Блокировки (Locking)** — транзакция блокирует строки, другие ждут. Простой подход, но читатели блокируют писателей. Бывают:
	1. **Read Committed (закоммиченное чтение)** — каждый запрос внутри транзакции видит только уже закоммиченные данные, но два одинаковых `SELECT` могут вернуть разные результаты, если между ними другая транзакция сделала `COMMIT`. Это уровень по умолчанию в PostgreSQL.
	2. **Repeatable Read (повторяющееся чтение)** — вся транзакция видит один snapshot данных. Повторный `SELECT` вернёт те же данные, даже если другие транзакции уже что-то изменили и закоммитили.
	3. **Serializable (сериализуемый)** — максимальная изоляция. PostgreSQL делает так, будто конкурентные транзакции выполнялись строго по очереди. При конфликте одну из транзакций может отменить с `serialization failure`, и приложение должно повторить её.
По уровню строгости: `Read Committed → Repeatable Read → Serializable`.

- **MVCC (Multi-Version Concurrency Control)** — каждая транзакция видит свой snapshot данных. Высокий параллелизм, но накапливаются старые версии (нужен VACUUM)

PostgreSQL и Oracle используют MVCC. MySQL InnoDB — MVCC с блокировками.
