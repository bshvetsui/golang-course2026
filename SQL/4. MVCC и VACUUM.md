**MVCC (Multi-Version Concurrency Control)** — PostgreSQL не перезаписывает строки при UPDATE, а создаёт новую версию. Старая помечается как мёртвая (dead tuple).

Читатели не блокируют писателей. Обратная сторона — накопление мёртвых строк, которые требуют очистки через VACUUM.
## VACUUM
Очистка мёртвых строк (dead tuples), которые больше не видны ни одной транзакции.

- **VACUUM** — помечает место как свободное для переиспользования. Не блокирует таблицу. Используется для регулярного обслуживания
- **VACUUM FULL** — полностью перезаписывает таблицу, освобождает место на диске. Берёт Exclusive lock, таблица недоступна. Применяется когда много места занято мёртвыми строками
- **VACUUM ANALYZE** — VACUUM с обновлением статистики для планировщика. Не блокирует таблицу. Запускается после массовых изменений
## VACUUM vs VACUUM FULL
- **VACUUM** — место остаётся в файле таблицы, быстро, без блокировки, для регулярного использования
- **VACUUM FULL** — место возвращается ОС, медленно, Exclusive lock, крайний случай
## Autovacuum
Фоновый процесс, который автоматически запускает VACUUM.
Срабатывает когда dead tuples превышают порог (по умолчанию 50 + 20% от размера таблицы) или давно не было vacuum.
Основные настройки: `autovacuum_vacuum_threshold` (минимум dead tuples), `autovacuum_vacuum_scale_factor` (процент от таблицы), `autovacuum_naptime` (интервал проверки).
На больших таблицах autovacuum может не успевать — растёт bloat.

## Bloat
Раздутие таблицы из-за мёртвых строк.

Признаки: таблица занимает больше места чем данные, запросы медленнее из-за чтения лишних страниц.

Решения: настроить autovacuum агрессивнее, VACUUM FULL (с даунтаймом), `pg_repack` (без блокировки).
## Transaction ID Wraparound
PostgreSQL использует 32-bit transaction ID. После ~2 млрд транзакций происходит wraparound.

Если не делать VACUUM, старые данные станут невидимыми. Autovacuum принудительно запускается при приближении к лимиту (агрессивный режим).
