1. **Producer** — сервис, который отправляет сообщение exchange (распределителю).
2. **Exchange** — это распределитель сообщений, решает, в какую очередь их отправить.
	1. **Direct** — отправляет сообщение в конкретную очередь по точному имени-метке.  
	    Пример: метка `email` → очередь `email`.
	2. **Topic** — отправляет сообщения по шаблону.  
	    Пример: `order.created` или `order.paid`.  
	    `*` — любое одно слово, `#` — любое количество слов.
	3. **Fanout** — отправляет копию сообщения во все подключённые очереди.  
	    Пример: событие получают уведомления, аналитика и логи.
	4. **Headers** — выбирает очередь по дополнительным полям сообщения.  
	    Используется редко, потому что сложнее настраивать.
3. Binding - связь между exchange и queue. Содержит routing key(метка например при direct exchange) или headers, по которым exchange решает, в какую queue направить 
4. **Queue** — буфер для хранения сообщений. Сообщение хранится в queue до подтверждения обработки consumer'ом. Queue может быть durable (переживает перезагрузку broker'а) или transient (временная очередь, и не должна использоваться для важных данных)
5. **Consumer** — получает сообщения из queue. После обработки отправляет ACK broker'у для подтверждения
	1. **Auto ACK** — broker удаляет сообщение сразу после отправки consumer'у, не дожидаясь обработки. Максимальная скорость, но при падении consumer'а сообщение теряется
	2. **Manual ACK** — consumer явно вызывает `basic.ack` после успешной обработки. Broker удаляет сообщение только после получения подтверждения. Гарантирует at-least-once
	3. **NACK** — consumer вызывает `basic.nack` для отказа от сообщения. Сообщение может быть возвращено в queue для повторной доставки или отправлено в DLX и Retry
	4. **Reject** — аналогичен NACK, но работает с одним сообщением. Используется для отклонения невалидных сообщений
## Dead Letter Exchange (DLX) - очередь для сообщений которые не смогли обработать
Нужна для ретраев, аналитики, отлова событий которые всегда туда попадают
**RabbitMQ не имеет нативного механизма отложенных повторов. Retry реализуется через цепочку DLX + delay queue (после истечения TTL очередь делает ретрай)**

Сюда попадают через:
1. **NACK** — временная ошибка (БД упала, таймаут)
2. **Reject** — битое сообщение, невалидный формат
3. **TTL истёк** — TTL ставится через свойство `expiration` - на сообщение, `x-message-ttl` - на очередь
4. **Queue переполнена** 
## Prefetch 
**Prefetch** настраивается через `basic.qos(prefetch_count=N)` и ограничивает, сколько сообщений RabbitMQ может заранее выдать consumer’у без ACK. Например, при `prefetch_count=10` consumer получит максимум 10 неподтверждённых сообщений. Это защищает его от перегрузки и помогает равномернее распределять работу между consumer’ами.

## Масштабирование
**Масштабирование RabbitMQ** обычно делают добавлением нескольких consumer’ов к одной queue.
## Horizontal Scaling
Broker распределяет сообщения между consumer’ами по кругу через **round-robin delivery**:
1. Первое сообщение → consumer 1.
2. Второе → consumer 2.
3. Третье → consumer 3.
4. Следующее снова → consumer 1.
RabbitMQ масштабируется количеством consumer’ов. Но throughput одной queue ограничен производительностью одного broker’а. Для большей нагрузки создают несколько queue и распределяют сообщения через exchange с **consistent hashing**_(сообщения с одинаковым ключом всегда направляются в одну и ту же queue)_.
## Порядок сообщений
Порядок сохраняется только при одном consumer’е на queue. При нескольких consumer’ах сообщения выдаются по порядку, но обрабатываются с разной скоростью, поэтому результат может прийти не по порядку.

**Redelivery** тоже может нарушить порядок: если consumer отправил NACK или упал без ACK, сообщение возвращается в queue и доставляется повторно.
## Classic Queue
Classic queue обычно хранится на одном узле. Старое зеркалирование очередей больше не рекомендуется и удалено из новых версий RabbitMQ.
## Quorum Queue
**Quorum queue** — современная отказоустойчивая очередь. Сообщения копируются на несколько узлов.
1. Один узел становится **leader**.
2. Остальные узлы — **followers**.
3. Producer отправляет сообщение leader’у.
4. Leader копирует сообщение на followers.
5. Запись подтверждается только после сохранения на большинстве узлов.
Если leader падает, один из followers становится новым leader.
**для важных очередей используют quorum queue и минимум три узла RabbitMQ.**
## Если сеть разделилась
Часть кластера, где осталось большинство узлов, продолжает принимать сообщения. Меньшая часть перестаёт принимать записи, чтобы не появились разные версии данных.
## Минус Quorum Queue
Она надёжнее classic queue, но работает немного медленнее, потому что каждое сообщение нужно скопировать на несколько узлов.
