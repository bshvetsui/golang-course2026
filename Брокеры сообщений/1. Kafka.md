Брокер сообщений, нужен чтобы передавать данные между микросервисами асинхронно.
Чтобы если упадет сервис - у нас останется данные которые он оставит в кафке, чтобы другие сервисы продолжили с ним работу
1. Producer - тот кто передает данные кафке. Делает в 5 этапов:
	1.  **Serialization** — producer делает из обьекта который отправляет в кафку байтовый массив, потому что она не умеет работать с обьектами
	2. Partitioning - определяет в какую партицию пойдём
	3. **Batching** —у producer есть общий буфер памяти, логически разделённый тоже по partitions, там мы накапливаем и батчим (отправляем). Параметр `batch.size` задаёт максимальный размер пакета, `linger.ms` — время ожидания заполнения батча
	4. **Send** — фоновый Sender Thread забирает готовые батчи и группирует их по broker'ам. Если один broker является leader'ом нескольких partition'ов, батчи отправляются одним сетевым запросом
	5. **ACK** — broker записывает данные и отправляет подтверждение в зависимости от настройки `acks`. 
		1. **acks=0** быстро потому что не подтверждаем, поэтому иногда теряем данные
		2. **`acks=1`** — producer ждёт подтверждения только от leader'а. Потеря возможна при падении leader'а до репликации
		3. **`acks=all`** — producer ждёт подтверждения от всех реплик в ISR. Максимальная надёжность при правильной настройке `min.insync.replicas`
2. Consumer - тот кто читает
## Структура 
1. **Broker** — узел Kafka-кластера (аналог worker node в k8s, тоже нужно держать минимум 3). Хранит данные partition'ов и обслуживает запросы клиентов.
2. **Topic** — логическая категория сообщений. Например orders, payments, delivery, notifications. Producer записывает сообщения в topic, Consumer читает из него. Topic делится на partition'ы чтобы читать данные параллельно (по той же причине делают например репликацию БД чтобы читать данные быстрее)
3. **Partition** — упорядоченный лог внутри topic'а, содержит .log .index .timeIndex. Каждое сообщение получает уникальный offset внутри partition'а. ТОЛЬКО ЗДЕСЬ ЕСТЬ ГАРАНТИЯ FIFO
4. **Offset** — позиция сообщения которое нам надо прочитать в .log файле в partition. Монотонно растёт, принадлежит конкретному partition'у
## Как читать из Партиции данные по offset'у
Retention — сколько по времени и по обьему кафка хранит в топике данные.  
 1. **`retention.ms`** — максимальное время хранения сообщений. По умолчанию 7 дней. По истечении TTL сегменты удаляются
2. **`retention.bytes`** — максимальный объём данных в Partition. При превышении старые сегменты удаляются

## Репликация Брокеров
1. **Replica** — копия partition на другом broker'е. Обеспечивает отказоустойчивость при падении узлов
2. **Leader** — основная реплика partition'а. Producer и Сonsumer работают только с leader'ом
3. **Follower** — реплика, которая асинхронно копирует данные из leader'а. Служит кандидатом на leader election при падении текущего leader'а
4. **ISR** — это реплики, которые успевают синхронизироваться с leader. Если leader упадёт, новая leader выбирается из ISR. Отставшая реплика временно исключается из ISR.
## Где хранятся данные
1. **ZooKeeper** — внешний сервис, хранит метаданные в ZNodes, использует Watchers для уведомлений. Плохо масштабируется и сложный. В основном легаси
2. **KRaft** — встроен в Kafka, хранит метаданные в Metadata Log, использует Raft consensus. Масштабируется и прост
## Защита от потерь
1. **acks=all** — producer ждёт подтверждения от всех ISR реплик.
2. **min.insync.replicas=2** — запись запрещена, если осталось меньше двух ISR реплик.
3. **unclean.leader.election.enable=false** — отставшая реплика не станет leader, чтобы не потерять данные.
4. **enable.idempotence=true** — повторная отправка не создаст дубликат.
5. **retries** **и** **delivery.timeout.ms** — producer повторяет отправку при временной ошибке.
6. **Manual commit** — consumer сохраняет offset только после успешной обработки.
