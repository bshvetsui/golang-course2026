1. **Database per Service** — у каждого Go-сервиса своя PostgreSQL БД/схема. `Order Service` не делает `SELECT` из таблиц `Payment Service`, а получает данные через API или Kafka. Это уменьшает связанность сервисов.
    
2. **Saga** — бизнес-операция разбивается между несколькими Go-сервисами. Пример: `Order → Payment → Delivery`. Каждый сервис делает свою транзакцию в PostgreSQL. Если `Payment` упал — отправляем событие `PaymentFailed`, после чего `Order Service` отменяет заказ. Бывает **Orchestration** (отдельный сервис управляет шагами) и **Choreography** (сервисы общаются событиями через Kafka).
    
3. **Transactional Outbox** — решает проблему `PostgreSQL записал данные, Kafka не получила событие`. Go-сервис в одной транзакции пишет `orders` + `outbox`. Отдельный worker читает `outbox` и отправляет события в Kafka.
    
4. **Transactional Inbox** — защищает consumer от повторной обработки Kafka-сообщения. Go-consumer получает `message_id`, проверяет/записывает его в PostgreSQL `inbox`. Если такой ID уже есть — повторно бизнес-логику не выполняет.
    
5. **Eventual Consistency** — базы разных сервисов синхронизируются не мгновенно. Например, `Order Service` уже записал заказ в PostgreSQL и отправил событие в Kafka, а `Payment Service` обработает его через несколько миллисекунд/секунд. Временно состояния разные, позже становятся согласованными. Это про CAP
    
6. **Event Sourcing** — в PostgreSQL храним события вместо только текущего состояния: `OrderCreated → OrderPaid → OrderShipped`. Состояние заказа восстанавливается из этих событий. Kafka часто используется для распространения событий другим сервисам.
    
7. **CQRS** — разделяем запись и чтение. Например, Go API пишет заказ в PostgreSQL через `Command`, а для быстрых `GET` используется отдельная read-модель, которая обновляется событиями из Kafka. `Command = изменить`, `Query = прочитать`.
