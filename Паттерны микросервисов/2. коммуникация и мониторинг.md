## Коммуникация

### 1. API Gateway
**API Gateway** — единая точка входа во все микросервисы.
`Client → Gateway → Go services → PostgreSQL / Kafka`
Пример: `GET /orders/42` → Gateway отправляет запрос в `order-service`. Может дополнительно делать authentication, rate limit, TLS, routing.
### 2. Backend for Frontend (BFF)
**BFF** — отдельный backend, который собирает данные специально под конкретный frontend.
`React → BFF → user-service + order-service`
Например страница профиля требует пользователя и его заказы. React делает **1 запрос в BFF**, а BFF вызывает несколько Go-сервисов и собирает единый JSON.
### 3. Service Mesh
**Service Mesh** — инфраструктурный слой для коммуникации **между сервисами**.
`order-service → Service Mesh → payment-service`
Берёт на себя `mTLS`, retries, load balancing, tracing, traffic routing. Go-сервис занимается бизнес-логикой, а инфраструктурные задачи выполняет, например, `Istio/Linkerd`.

### 4. Request/Response vs Event-driven
**Request/Response** — сервис вызывает другой сервис и ждёт ответ:
`order-service → HTTP/gRPC → user-service → response`
Используется, когда результат нужен сразу: проверить пользователя, получить цену, проверить баланс.

**Event-driven** — сервис публикует событие и не ждёт обработчиков:
`order-service → Kafka[OrderCreated] → payment / notification`
Например Go-сервис сохраняет заказ в PostgreSQL → публикует `OrderCreated` в Kafka → другие сервисы независимо его обрабатывают.
## Мониторинг

### 5. Health Check
**Health Check** — endpoint, показывающий состояние Go-приложения.
`GET /health → 200 OK`

Обычно:  
`liveness` — процесс вообще работает.  
`readiness` — приложение готово принимать трафик, например доступен PostgreSQL.
Kubernetes использует проверки, чтобы не отправлять трафик сломанным pod'ам и перезапускать зависшие.
### 6. Centralized Logging
**Centralized Logging** — логи всех микросервисов собираются в одном месте.
`Go services → stdout → Loki/ELK → Grafana`

Вместо просмотра логов каждого pod отдельно можно найти:
`request_id=abc123 → gateway → order-service → PostgreSQL error`
Go-приложение обычно пишет структурированные JSON-логи: `level`, `service`, `request_id`, `error`.

### 7. Distributed Tracing
**Distributed Tracing** — показывает весь путь одного запроса через несколько сервисов.
`Client → Gateway → order-service → payment-service → PostgreSQL/Kafka`
Каждый запрос получает `trace_id`, поэтому видно, **в каком именно сервисе возникла задержка или ошибка**.

Обычно: `OpenTelemetry → Jaeger/Tempo`.
