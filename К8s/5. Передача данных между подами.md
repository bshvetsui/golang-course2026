### 1. Контейнер → контейнер внутри одного Pod
Контейнеры внутри Pod общаются через `localhost`. Например backend на `8080` может обратиться к sidecar на `localhost:9090`. Потому что все контейнеры одного Pod используют одно **сетевое пространство Linux (`network namespace`)**
### 2. Pod → Pod на одной Node
Каждый Pod имеет свой **PodIP** — обычный внутренний IP Pod, например `10.244.1.5`. Внутри Pod есть сетевой интерфейс `eth0` — грубо говоря, его виртуальная сетевая карта.  
Чтобы подключить эту виртуальную сетевую карту к сети Node, обычно используется **veth pair** — пара связанных виртуальных интерфейсов: один конец находится внутри Pod (`eth0`), второй — в сетевом пространстве самой Node. Всё, что входит в один конец, выходит из второго.  
Например два Pod находятся на одной Node: `Pod A = 0.0.0.1`, `Pod B = 0.0.0.2` Когда A отправляет запрос B:
1. Pod A уже знает IP назначения 0.0.0.2` и отправляет пакет через свой `eth0`.
2. Через `veth pair` пакет попадает из Pod в сетевое пространство Node.
3. Дальше CNI определяет, каким путём доставить пакет к Pod B. 
   В зависимости от CNI это может быть Linux bridge (`cni0`, `cbr0`) либо обычная маршрутизация Linux/eBPF
4. Если используется Linux bridge, через **ARP** (стандартный протокол определения MAC по ip) определяется MAC-адрес интерфейса, соответствующего известному IP. ARP не ищет IP — IP уже известен.
5. Пакет попадает во второй `veth`, затем в `eth0` Pod B.  
    Упрощённо: `Pod A eth0 → виртуальный кабель veth → сеть Node → veth → Pod B eth0`.
### 3. Pod → Pod на разных Node через прямую маршрутизацию
1. Node1 должна понимать, что IP нужного Pod находится на Node2.  
2. Каждой Node выделяется диапазон адресов для её Pod’ов — **PodCIDR**
3. У Linux на каждой Node есть **routing table (таблица маршрутизации)** — обычная таблица вида «если пакет идёт в такую сеть, отправлять его через такую ноду». Эти маршруты можно раздавать автоматически через **BGP**.
 4. BGP — протокол, которым маршрутизаторы сообщают друг другу: «такая сеть доступна через меня». В Kubernetes Node фактически могут выступать небольшими маршрутизаторами для своих Pod-сетей.  
 5. Linux kernel (ядро линукса) по выстроенному BGP маршруту отправляет в **Pod B**
 
Например с Calico:
1. На Node2 создаётся Pod и получает 0.0.0.2
2. **Felix** — агент Calico, работающий на Node — настраивает Linux-сеть: интерфейсы, маршруты, сетевые политики.
3. BGP-компонент Calico сообщает другим Node, что `10.244.2.0/24` доступна через Node2.
4. Node1 добавляет это знание в свою Linux routing table.
5. Теперь пакет идёт путём: `Pod A → Node1 → физическая сеть → Node2 → Pod B`.  

### 4. Что происходит, если Pod удалился или переехал

Если Pod/Pod-сеть больше недоступны через Node, CNI обновляет сетевое состояние. При использовании BGP изменения маршрутов распространяются между Node, после чего обновляются их routing tables. Поэтому приложениям не приходится знать, на какой физической Node находится другой Pod — сетевой слой Kubernetes/CNI занимается этим сам.

### 5. Pod → Pod на разных Node через Overlay

Есть другой способ: **не заставлять физическую сеть вообще знать про PodIP**.  
Допустим физическая сеть умеет доставлять только между `Node1 = 192.168.1.10` и `Node2 = 192.168.1.20`, но ничего не знает про Pod `10.244.1.5` и `10.244.2.7`.  
Тогда используется **overlay-сеть**. Например **VXLAN** — технология, которая позволяет передавать внутренний пакет Pod’а внутри обычного сетевого пакета между Node.  
Пусть Pod A хочет отправить пакет Pod B. Исходно внутри пакета написано: `от 10.244.1.5 → к 10.244.2.7`. Node1 понимает, что Pod B находится на Node2, и временно **инкапсулирует пакет** — то есть буквально помещает исходный пакет внутрь другого пакета. Снаружи получается адресация `Node1 192.168.1.10 → Node2 192.168.1.20`, а внутри остаётся исходный `Pod A → Pod B`.  
Физическая сеть видит только NodeIP и спокойно доставляет пакет на Node2. Node2 снимает внешнюю оболочку (**декапсуляция**) и получает первоначальный пакет для `10.244.2.7`, после чего передаёт его Pod B.  
То есть VXLAN можно представить как посылку в коробке: **внутренняя посылка адресована Pod → Pod, внешняя коробка адресована Node → Node**.

### 6. Прямая маршрутизация и Overlay

Это два разных нормальных варианта сети Kubernetes.

1. **Direct routing/BGP** — Node и/или физические маршрутизаторы знают, где находятся Pod-сети. Пакет идёт без дополнительной сетевой оболочки: `Pod → Node1 → Node2 → Pod`.
    
2. **Overlay/VXLAN** — физическая сеть знает только NodeIP. Pod-пакет упаковывается внутрь Node-пакета: `Pod → Node1 → [упаковка] → Node2 → [распаковка] → Pod`.  
    Overlay не является «старым легаси». Он часто удобнее, потому что не требует настраивать физическую сеть под PodIP. Direct routing обычно проще по пути самого пакета и не имеет overhead от туннеля.
    

### 7. Где здесь CNI

**CNI (Container Network Interface)** — механизм/стандарт, через который Kubernetes подключает Pod к сети. Конкретные реализации: Calico, Cilium, Flannel.  
Когда создаётся Pod, CNI в зависимости от реализации выдаёт ему IP, создаёт/настраивает сетевой интерфейс, маршруты и правила доступа. Он **не спрашивает kube-apiserver, куда отправить каждый отдельный пакет**. CNI заранее настраивает Linux kernel, после чего пакеты проходят по уже готовым правилам.  
Например в Calico агент `Felix` заранее настраивает Linux networking. В Cilium большую часть этой работы делают программы **eBPF** внутри Linux kernel.

### 8. CNI и Service — разные уровни

Всё выше отвечает на вопрос: **как доставить пакет, когда конкретный `PodIP` уже известен**.  
Но обычно backend обращается не напрямую к `10.244.2.7`, а к Kubernetes `Service`, например `postgres:5432`. У Service есть стабильный `ClusterIP`, а за ним может находиться несколько Pod.  
Тогда сначала происходит выбор конкретного Pod: `Service ClusterIP → PodIP`, а затем уже CNI доставляет пакет до этого `PodIP`.  
Поэтому общую картину удобно запомнить так: **`Service/kube-proxy` выбирает, в какой Pod отправить запрос; `CNI` обеспечивает физическую сетевую доставку до этого Pod.**  
И совсем коротко по терминам: `eth0` — виртуальная сетевая карта Pod; `PodIP` — IP Pod; `veth pair` — виртуальный кабель Pod↔Node; `PodCIDR` — диапазон IP для Pod’ов; `routing table` — таблица «куда отправлять пакет» внутри Linux; `BGP` — протокол обмена маршрутами; `Felix` — сетевой агент Calico; `VXLAN` — туннель, который упаковывает Pod-пакет внутрь пакета Node→Node.
