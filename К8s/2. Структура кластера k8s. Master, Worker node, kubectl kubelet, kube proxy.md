## Мастер ноды и воркер ноды (узлы)
1. В отказоустойчивом кластере **должно быть 3 мастер нод**
2. Это помогает избежать ситуации когда связь между группами мастер-нод или между всеми нодами одновременно нарушается, и каждая изолированная нода/группа начинает считать себя полноценным кластером. Это приводит к проблемам с консистенцией данных в etcd
3.  **Воркер нод любое количество** - зависит от нагрузки, которую хотим выполнять
## Мастер-нода - kubectl
1. **API сервер (KubeAPI)** - С ним взаимодействуют все компоненты. Он является центральным узлом. Он принимает и обрабатывает запросы по restapi(json и yaml)
2. **Kube Conroller manager** - Это группа служб, которая  следит за состоянием кластера. И которая вносит изменения для приведения фактического состояния кластера к желаеому. Мы говорим куберу что мы хотим видеть в конечном статусе.
3. **Kube scheduler** - Распределяет рабочую нагрузку по доступным узлам. Он планирует на каком узле запустить то или иное приложение
4. **etcd** Распределенное хранилище. Ключ-значение. Хранит инфу о состоянии кластера.
## Воркер-нода - kublet, kube proxy
**kublet** - cлужба, которая опрашивает апи сервер какие поды предназначены текущему узлу. И запускает, удаляет их через **container runtime engine** (например docker)
Также информирует api сервер о статусе работающих подов на узле.
1. **kube proxy** - Компонент, управляющий сетевыми настройками узла.
	1. endpoint k8s сервиса = это ip адрес + порт пода
	2. kube proxy отслеживает изменения сервисов и их эндпоинтов через Api k8s и настраивает правила маршрутизации на уровне узла с помощью iptables 
	   *(или IPVS ( использует ядро для более хай перфоманс балансировки) узнать -  `k describe svc/<svc-name>`.)
	3. По умолчанию (iptables mode) kubeproxy создает правила iptables, которые перехватывают трафик, направленный на clusterIP и порт сервиса. выполняют destination NAT: подменяют адрес назначения с ClusterIP на одного из ip эндпоинта сервиса. 
	4. kube proxy занимается только подменой адреса назначения и балансировкой а не маршрутизацией между узлами - этим занимается CNI
	5. Можно сбросить все правила командой `iptables -F`. Кубу по дефолту надо 30 секунд что бы понять что праивл нет и восстановить их. либо 10 секунд по дефолту что бы обновить правила маршрутизации при изменении эндпоинтов 
2. **Container runtime** (docker) - компонент, взаимодействующий с контейнером.
## Механизм работы мастер ноды. Создание пода
1. **kubectl** отправляет запрос к **KubeAPI** - `kubectl run my-pod` 
2. **kubeAPI** аутентифицирует запрос, проверяет права отправителя, спрашивает **Conroller manager** есть ли ресурсы и если все ок записывает в **etcd**
3. **Kube Scheduler** - периодически спрашивает **kubeAPI** надо ли создавать что то, и если надо - смотрит на какую менее нагруженную ноду можно закинуть под, и когда находит место - отвечате **kubeAPI**
4. **Kubeapi** обращается в **kubelet** той ноды, на которую указал kube Scheduler и **kubelet** дает комманду **Container runtime engine** на создание пода
*Под не может создастся на 2ух разных узлах, в etcd есть поле **node**.
