## syscall
Приложение **не работает с железом напрямую**. Оно обращается к ядру через **system call (syscall)**, а kernel уже управляет ресурсами. В backend приложениях число syscall стараются минимизировать.
Профилирование:
```sh
ps aux                 # посмотреть процессы типа диспетчера задач
top                    # посмотреть кто использует сколько CPU/RAM
free -h                # память сколько используется
ls -l /proc/1234       # данные процесса, по PID
ss -lntp               # Проверить открытые sockets. socket - открытое соединение
strace -p 1234         # какие syscalls делает процесс по PID
```

### `dmesg` — лог сообщений Kernel
Через него ищут проблемы с OOM Killer,  I/O, файловой системой и т.п. Вывод очень большой и обычно фильтруют строку:
```sh
dmesg | grep -i oom # OOM Killer
dmesg | grep -i "I/O error" # ошибка передачи даннных
dmesg | grep -i eth # подкючение сокетов
dmesg | grep -i ext4 # файловая система
```
**OOM Killer**
Если системе критически не хватает RAM, kernel должен освободить память и может **убить один из процессов**.

### `sysctl` — параметры Kernel
`sysctl` позволяет читать и изменять **runtime-параметры ядра**. Например временно изменить
```sh
sudo sysctl -w net.ipv4.ip_forward=1
sudo sysctl --system # применить изменения
```
```
важные группы:
net.*     → networking
vm.*      → память
fs.*      → filesystem / file descriptors
kernel.*  → общие параметры ядра
```
