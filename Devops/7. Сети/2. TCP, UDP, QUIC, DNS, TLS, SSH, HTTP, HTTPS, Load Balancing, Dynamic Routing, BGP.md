## 10. TCP, UDP и QUIC

1. **TCP** — НАДЕЖНЫЙ транспортный протокол передачи данных в сетях TCP/IP, предварительно устанавливающий соединение с сетью. Используется для передачи данных (электронная почта, файлы, сообщения). При определении потери пакетов будет выполнен перезапрос потерянных пакетов.
2. **UDP** — протокол, передающий сообщения-датаграммы без необходимости установки соединения, используется в потоковой передаче данных (IPTV, VoIP)

   **для проверки доступности UDP nmap - sU можно использовать**
1. **QUIC** работает поверх UDP и сам реализует надёжность, congestion control (контроль перегрузки), TLS и multiplexing (несколько независимых потоков).
2. **HTTP/1.1 и HTTP/2** обычно работают поверх TCP. **HTTP/3**, стандартизованный в 2022 году, работает поверх QUIC.
## 11. Установка TCP-соединения

TCP использует **three-way handshake**:

1. Клиент → сервер: `SYN` флаг (флаг запроса).
2. Сервер → клиент: `SYN + ACK`(всё ок) или `RST`(не надо со мной соединятся).
3. Клиент → сервер: `ACK` или если клиент ничего не шлет - истекает таймаут у сервера и он закрывает сокет.

После этого состояние соединения `ESTABLISHED`, и начинается передача данных.
`RST` — немедленный сброс соединения.

## 12. Поддержание TCP-соединения и ACK

TCP нумерует передаваемые данные через sequence numbers и подтверждает получение через ACK. Если нужный ACK не получен вовремя, данные отправляются повторно.

ACK — общая идея **«я получил/обработал»**, есть например в Kafka, RabbitMQ

## 13. DNS

фундаментальная технология современной интернет-среды, которая отвечает за хранение и обработку информации о доменных адресах. Нужен для того, чтобы соотносить айпи адреса с доменными именами.

**DNS использует в 99% случаев UDP**, TCP слишком долгий
1. Пока устраиваешь TCP-сессию, ты можешь 3 раза отправить UDP пакетик туда и получить его обратно.
2. Устанавливает TCP только когда данных очень много, и критично их потерять (например трансфер зоны)

Основная инфа которую он хранит:
1. `A` — IPv4.
2. `AAAA` — IPv6.
3. `CNAME` — alias на другое DNS-имя.
4. `MX` — почтовые серверы.
**FQDN** — полное DNS-имя, например `api.example.com`.

## 14. Recursive и authoritative DNS

Клиент обычно отправляет запрос **recursive resolver** (DNS-серверу, который найдёт ответ за клиента).

1. **Recursive resolver** — просто обращаетесь к серверу, а он, если не найдет у себя нужной записи, идет к другим серверам и спрашивает у них.
2. **Non-recursive resolver** — "я не знаю, но спроси у этого сервера". И клиент будет слать ещё один запрос. Понятное дело, что при медленном интернете первый вариант лучше.

3. **Authoritative DNS** — хранит официальные DNS-записи конкретной зоны.
4. **Authority section** в DNS-ответе содержит информацию об authoritative зоне

## 15. TCP и UDP у разных протоколов

1. DNS обычно использует `UDP/53`; при больших ответах и некоторых операциях может использовать `TCP/53`.
2. HTTP/1.1 и HTTP/2 — TCP.
3. HTTP/3 — QUIC поверх UDP.
4. SSH — TCP.
5. PostgreSQL — TCP.
6. ICMP не использует ни TCP, ни UDP.

## 16. TLS, SSL и SNI

**SSL** — старые протоколы; сейчас используется **TLS**.

**TLS**:
1. Клиент подключается к серверу и начинает **TLS handshake** — этап, на котором клиент и сервер договариваются о шифровании перед передачей обычных данных.

2. Сервер отправляет **TLS-сертификат** и свой **временный public key**. Сертификат нужен, чтобы клиент мог проверить подлинность сервера.

3. Клиент проверяет сертификат через доверенные центры сертификации 

4. Клиент создаёт свои временные **private key + public key**. `Private key` оставляет у себя, а `public key` отправляет серверу.

5. Теперь у клиента есть **свой private key + public key сервера**, а у сервера — **свой private key + public key клиента**. Из этих данных обе стороны математически получают **одинаковый общий секрет**. Сам общий секрет по сети никто не отправляет.

6. Сервер отдельно использует **private key своего сертификата**, чтобы поставить цифровую подпись и доказать клиенту, что сертификат действительно принадлежит ему.

7. Из общего секрета клиент и сервер создают **сеансовые симметричные ключи** и дальше шифруют ими весь трафик.

Важно различать два вида ключей у сервера: **временный private/public key** нужен для получения общего секрета, а **private key сертификата** — для подтверждения личности сервера.

**Connection: keepAlive HTTP заголовок** - механизм в протоколе HTTP, который позволяет поддерживать одно TCP-соединение открытым для нескольких последовательных запросов

**SNI** — hostname в TLS ClientHello. Он нужен, чтобы сервер с одним IP и множеством сайтов понял, сертификат какого сайта нужно отдать клиенту.

## 17. Симметричное и асимметричное шифрование

**Симметричное** — один общий ключ, быстрое, используется для основного трафика. **Асимметричное** — public/private key, медленнее, используется при установлении доверия 

TLS сочетает оба подхода: 
TLS использует асимметричную криптографию, Из полученного общего секрета обе стороны создают **симметричные сеансовые ключи** для общения
## 18. Проверка HTTPS-сертификата

Браузер проверяет:

1. Домен совпадает с `SAN` сертификата.
2. Сертификат не истёк.
3. Подпись сертификата корректна.
4. Certificate chain ведёт к доверенному `Root CA`.

Обычно цепочка выглядит как `site certificate → Intermediate CA → Root CA`.

## 19. SSH

SSH работает поверх TCP, обычно `22/tcp`.

1. Сначала устанавливается TCP.
2. Затем SSH договаривается о шифровании.
3. Клиент проверяет host key сервера через `known_hosts`.
4. При password auth сервер проверяет пароль.
5. При SSH-key auth сервер хранит public key в `authorized_keys`, а клиент доказывает владение private key.

`known_hosts` — клиент проверяет сервер. `authorized_keys` — сервер проверяет клиента.

## 20. HTTP

HTTP — прикладной протокол request/response. Клиент отправляет запрос, например `GET /api/users`, сервер возвращает HTTP response.

Основные версии: HTTP/1.1 → TCP, HTTP/2 → TCP + multiplexing, HTTP/3 → QUIC/UDP + независимые streams.

## 21. Basic Authentication

Basic Auth передаёт:

```text
Authorization: Basic base64(username:password)
```

Base64 — не шифрование, поэтому Basic Auth должен использоваться только вместе с HTTPS.

## 22. Полный путь HTTPS-запроса

При открытии `https://yandex.ru` примерно происходит:

1. Браузер получает IP через DNS.
2. Linux смотрит `ip route` и выбирает маршрут.
3. Для локального next hop через ARP/neighbor cache определяется MAC.
4. Пакет отправляется на default gateway.
5. Router/NAT при необходимости меняет private source IP на public IP.
6. Маршрутизаторы Интернета доставляют пакеты к сети назначения.
7. Для HTTP/1.1 или HTTP/2 устанавливается TCP через `SYN → SYN/ACK → ACK`.
8. Для HTTP/3 вместо TCP используется QUIC/UDP.
9. Выполняется TLS handshake, проверяется certificate, через SNI выбирается нужный сайт.
10. Браузер отправляет HTTP request.
11. Запрос может пройти через CDN/load balancer/reverse proxy - nginx или envoy
12. Backend формирует response.
13. Браузер получает через nginx(конкретно здесь используется для хранения статики) HTML/CSS/JS/images  и отображает страницу.

## 23. L4 и L7 load balancer

1. **L4 LB** работает с IP, TCP/UDP и портами. Например: `:443 → backend1/backend2`.
2. **L7 LB** понимает HTTP и может маршрутизировать по `Host`, URL, header, cookie.
3. L7 также может делать **TLS termination** (расшифровать HTTPS на балансировщике).
4. Чистый L4 не понимает `/api`, `Host: example.com` и HTTP headers.

## 24. Динамическая маршрутизация

Статические маршруты администратор прописывает вручную. Динамические routing protocols автоматически обмениваются маршрутами.

1. **OSPF** — маршрутизация внутри своей инфраструктуры.
2. **BGP** — маршрутизация между автономными системами (**AS**) и управление routing policy.

## 25. eBGP и iBGP

BGP работает поверх `TCP/179`.
**AS** (Autonomous System) — сеть одной организации под общим управлением.
1. **eBGP** — BGP между разными AS, требует чтобы маршрутизаторы были соединены.
2. **iBGP** — BGP внутри одной AS, могут быть соединены маршрутизаторами вне BGP
3. **AS_PATH** — список AS, через которые прошёл маршрут.
4. Для iBGP исторически нужен full mesh (каждый BGP-router соединён с каждым), поэтому в больших сетях используют **Route Reflector** (центрально распространяет iBGP routes).

## 26. Основные BGP attributes

1. **LOCAL_PREF** — какой выход из своей AS предпочтительнее; больше = лучше.
2. **AS_PATH** — через какие AS идёт маршрут; обычно короче = лучше.
3. **MED** — какую точку входа в AS предпочесть; обычно меньше = лучше.
4. **NEXT_HOP** — IP следующего router.
## 27. Выбор BGP-маршрута
Нужно соблюдать:
1. Выше `LOCAL_PREF`.
2. Короче `AS_PATH`.
3. Ниже `MED`.
4. eBGP обычно предпочтительнее iBGP.
5. Ниже IGP-cost до `NEXT_HOP`.

Точный алгоритм немного отличается между vendor implementations.

## 28. BGP peering

**BGP peering** — установленное BGP-соединение между двумя routers.

Обычно routers знают IP соседа, его ASN и поднимают TCP/179. В production дополнительно ограничивают, какие prefixes соседу можно принимать и какие ему можно анонсировать.
Для iBGP часто используют loopback IP, чтобы BGP-session не зависела от одного физического интерфейса.

## 29. BGP Blackhole

Blackhole route намеренно отправляет traffic «в никуда». Обычно используется для DDoS: маршрут до атакуемого IP помечается специальной BGP community, после чего провайдер отбрасывает этот traffic до того, как он перегрузит сеть.
