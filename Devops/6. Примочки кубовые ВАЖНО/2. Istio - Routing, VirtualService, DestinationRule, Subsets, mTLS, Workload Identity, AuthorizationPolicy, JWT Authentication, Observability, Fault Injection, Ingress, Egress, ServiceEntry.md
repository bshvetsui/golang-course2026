## 1. Routing
### 1.1 VirtualService
`VirtualService` определяет **куда должен идти трафик и как обрабатывать запрос**.
Основные возможности:
1. HTTP routing;
2. routing по URI;
3. routing по headers;
4. routing по HTTP method;
5. retries;
6. timeout;
7. traffic splitting;
8. redirect;
9. rewrite;
10. fault injection.
Например можно отправлять:
1. `90%` запросов в `v1`;
2. `10%` запросов в `v2`.
Это используется для **Canary Deployment**.
Также можно направить пользователей с определённым header в отдельную версию приложения.
### 1.2 DestinationRule
`DestinationRule` определяет **как работать с уже выбранным сервисом**.
Через него настраиваются:
1. subsets;
2. load balancing;
3. connection pools;
4. circuit breaking;
5. outlier detection;
6. TLS;
7. locality/failover.
Удобно запомнить:
1. **VirtualService — КУДА отправлять запрос.**
2. **DestinationRule — КАК работать с destination.**
### 1.3 Subsets
Subset — логическая группа Pod'ов одного Service.
Например Service `orders` содержит:
```yaml
version: v1
```
и:
```yaml
version: v2
```
В `DestinationRule` можно создать:
```yaml
subsets:
- name: v1
  labels:
    version: v1
- name: v2
  labels:
    version: v2
```
После этого `VirtualService` может направлять разное количество трафика в каждый subset.
Используется для:
1. Canary;
2. Blue/Green Deployment;
3. A/B testing.
## 2. Security
### 2.1 mTLS
Istio может автоматически использовать **Mutual TLS** между workload'ами.
mTLS обеспечивает:
1. шифрование трафика;
2. проверку identity клиента;
3. проверку identity сервера;
4. защиту service-to-service соединений.
Приложению при этом не обязательно самостоятельно управлять TLS-сертификатами.
Istio занимается:
1. выдачей сертификатов;
2. их обновлением;
3. workload identity;
4. проверкой сертификатов;
5. настройкой mTLS между proxy.
### 2.2 Workload Identity
Istio идентифицирует workload обычно через его Kubernetes ServiceAccount.
Identity может выглядеть примерно так:
```text
cluster.local/ns/shop/sa/frontend
```
Благодаря этому Istio может отличить:
1. `frontend`;
2. `payments`;
3. `orders`;
4. любой другой workload.
Это позволяет строить Zero Trust security внутри Kubernetes.
### 2.3 AuthorizationPolicy
`AuthorizationPolicy` определяет, **кто имеет право обращаться к сервису**.
Например можно разрешить:
```text
frontend -> orders
```
и запретить все остальные запросы.
Можно фильтровать доступ по:
1. workload identity;
2. namespace;
3. ServiceAccount;
4. HTTP method;
5. path;
6. host;
7. source;
8. JWT claims.
Таким образом авторизация между сервисами может выполняться на уровне Service Mesh, а не внутри каждого backend.
### 2.4 JWT Authentication
Через `RequestAuthentication` Istio может проверять JWT.
Envoy может валидировать:
1. подпись токена;
2. issuer;
3. audience;
4. claims;
5. срок действия.
Обычно `RequestAuthentication` используется вместе с `AuthorizationPolicy`.
Например можно разрешить `/admin` только пользователю с определённым claim.
## 3. Observability
Поскольку Envoy видит весь service-to-service traffic, Istio может автоматически собирать сетевую телеметрию.
Основные данные:
1. количество запросов;
2. RPS;
3. latency;
4. HTTP status codes;
5. ошибки соединения;
6. retries;
7. source service;
8. destination service;
9. объём переданного трафика.
Istio интегрируется с:
1. Prometheus;
2. Grafana;
3. Jaeger;
4. OpenTelemetry;
5. Kiali.
Это позволяет получать метрики и tracing без реализации всей сетевой observability отдельно в каждом сервисе.
## 4. Fault Injection
Istio умеет намеренно создавать сетевые ошибки для тестирования устойчивости системы.
Например:
1. добавить задержку;
2. вернуть HTTP error;
3. применить ошибку только к части запросов.
Используется для проверки:
1. retries;
2. timeout;
3. circuit breaker;
4. поведения приложения при деградации зависимостей.
## 5. Ingress / Egress
### 5.1 Ingress Gateway
Istio Ingress Gateway принимает трафик из внешней сети и направляет его в сервисы внутри mesh.
Может выполнять:
1. TLS termination;
2. host/path routing;
3. traffic splitting;
4. authentication;
5. authorization.
### 5.2 Egress Gateway
Egress Gateway используется для контроля исходящего трафика из mesh.
Например можно заставить все сервисы обращаться к внешнему API только через один контролируемый gateway.
Это полезно для:
1. security;
2. audit;
3. контроля внешних соединений;
4. ограничения доступа в Internet.
### 5.3 ServiceEntry
`ServiceEntry` добавляет внешний сервис в service registry Istio.
Например:
```text
api.stripe.com
```
После этого к внешнему сервису можно применять часть политик Istio:
1. routing;
2. TLS;
3. timeout;
4. retries;
5. traffic policies.
