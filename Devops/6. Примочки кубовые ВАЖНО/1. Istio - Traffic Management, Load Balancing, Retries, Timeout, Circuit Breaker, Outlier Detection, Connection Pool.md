
## 1. Что такое Istio
Istio — это **Service Mesh**, который выносит сетевую логику между сервисами из приложений в инфраструктуру.
### 1.1 Архитектура
В классическом режиме рядом с приложением работает **Envoy proxy**, через который проходит входящий и исходящий трафик.
`istiod` выступает как **Control Plane**: получает конфигурацию из Kubernetes/Istio CRD и раздаёт её Envoy.
1. `istiod` — управляет конфигурацией.
2. `Envoy` — реально обрабатывает трафик.
## 2. Traffic Management
### 2.1 Load Balancing
Envoy знает все endpoints Kubernetes Service и сам выбирает, в какой Pod отправить запрос.
Istio поддерживает разные алгоритмы балансировки:
1. `ROUND_ROBIN`
2. `LEAST_REQUEST`
3. `RANDOM`
4. consistent hashing
Настраивается через `DestinationRule`.
```yaml
trafficPolicy:
  loadBalancer:
    simple: LEAST_REQUEST
```
Таким образом, балансировка происходит на стороне proxy вызывающего сервиса.
### 2.2 Retries
Istio может автоматически повторить запрос, если backend вернул определённую ошибку или соединение не удалось установить.
Настраивается через `VirtualService`.
```yaml
http:
- route:
  - destination:
      host: orders
  retries:
    attempts: 3
    perTryTimeout: 1s
    retryOn: gateway-error,connect-failure,refused-stream
```
Envoy получает ошибку от одного instance и может повторить запрос к другому.
Приложение при этом вообще может не знать, что первая попытка завершилась ошибкой.
Важно учитывать, что слишком большое количество retries может вызвать **retry storm**: перегруженный сервис начинает получать ещё больше запросов из-за повторных попыток.
Поэтому retries обычно используют вместе с:
1. timeout;
2. circuit breaker;
3. retry budget;
4. outlier detection.
### 2.3 Timeout
Istio позволяет задавать максимальное время ожидания ответа от сервиса.
```yaml
http:
- route:
  - destination:
      host: orders
  timeout: 5s
```
Если backend не отвечает за указанное время, Envoy прекращает ожидание.
Также отдельно существует:
`perTryTimeout: 1s`
Это timeout одной retry-попытки.
Например:
1. общий timeout — `5s`;
2. каждая попытка — максимум `1s`;
3. retries — максимум `3`.
Timeout защищает вызывающий сервис от зависания на медленном backend.
### 2.4 Circuit Breaker
Circuit Breaker защищает backend от чрезмерной нагрузки.
Envoy может ограничивать:
1. количество TCP connections;
2. количество одновременных HTTP requests;
3. количество pending requests;
4. количество retries;
5. размер connection pool.
Пример:
```yaml
trafficPolicy:
  connectionPool:
    tcp:
      maxConnections: 100
    http:
      http1MaxPendingRequests: 100
      http2MaxRequests: 1000
      maxRetries: 10
```
Если лимиты достигнуты, Envoy может начать делать **fail fast**, а не продолжать отправлять запросы в перегруженный сервис.
Важно: Circuit Breaker в Envoy — это не только классическая схема `CLOSED / OPEN / HALF-OPEN`. В Envoy это прежде всего **ограничение ресурсов upstream-сервиса**.
### 2.5 Outlier Detection
Outlier Detection используется для автоматического обнаружения проблемных Pod'ов.
Например Kubernetes ещё считает Pod работоспособным, но он постоянно отвечает:
1. `500`;
2. `502`;
3. `503`;
4. connection reset.
Envoy отслеживает такие ошибки и может временно исключить конкретный endpoint из балансировки.
```yaml
trafficPolicy:
  outlierDetection:
    consecutive5xxErrors: 5
    interval: 10s
    baseEjectionTime: 30s
    maxEjectionPercent: 50
```
Например:
1. Pod получил 5 последовательных `5xx`;
2. Envoy считает его проблемным;
3. Pod временно исключается из load balancing;
4. через некоторое время Envoy снова может начать отправлять ему запросы.
Это называется **passive health checking**, потому что состояние backend определяется по реальному пользовательскому трафику.
### 2.6 Connection Pool
Envoy не создаёт новое TCP-соединение для каждого HTTP-запроса.
Он поддерживает пул существующих соединений и переиспользует их.
Можно настраивать:
```yaml
connectionPool:
  tcp:
    maxConnections: 100
    connectTimeout: 1s
  http:
    maxRequestsPerConnection: 100
```
Connection Pool:
1. уменьшает количество TCP handshakes;
2. уменьшает количество TLS handshakes;
3. ускоряет запросы;
4. ограничивает количество соединений к backend;
5. помогает защищать backend от перегрузки.
