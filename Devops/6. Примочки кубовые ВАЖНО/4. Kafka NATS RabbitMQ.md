## 1. Подключение приложений
Приложению передаются endpoint + credentials через `Secret`: 
1. Kafka `kafka:9092`, 
2. RabbitMQ `rabbitmq:5672`, 
3. NATS `nats:4222`. 
## 2. Security
1. **Kafka:** SASL (сервис дает креды) + ACL(авторизация) + TLS, права `produce/consume` на конкретные topics. 
2. **RabbitMQ:** users + permissions + vhost (~ namescpace для вирт. деления кластера) + TLS. 
3. **NATS:** users/accounts + publish/subscribe permissions + TLS; могут использоваться NKeys/JWT.
## 3. Надёжность
**Kafka:** обычно `replication.factor=3`, `min.insync.replicas=2`, producer `acks=all`. 
**RabbitMQ:** durable queues + persistent messages; для HA — quorum queues, обычно `3` replicas/nodes. 
**NATS JetStream:** обычно `replicas=3`, persistent `file` storage, durable consumers + ACK. 
## 4. Retention — что конкретно настраивать
**Kafka:** 
1. `retention.ms` — сколько хранить сообщения, например `604800000` = 7 дней; 
2. `retention.bytes` — максимальный размер partition, `-1` = без лимита;
3. `cleanup.policy=delete` — удалять старые сообщения, 
4. `compact` — оставлять последнее значение каждого key. 

**RabbitMQ:** 
1. `message-ttl` — время жизни сообщения, например `86400000` = 24 часа; 
2. `max-length` / `max-length-bytes` — максимальный размер queue; 
3. `expires` — удалить саму неиспользуемую очередь через заданное время.

1. `max_age` — например `24h`/`168h`; 
2. `max_bytes` — максимальный размер stream; 
3. `max_msgs` — лимит сообщений;

## 5. Retry / DLQ
**Kafka:** обычно отдельные retry/DLQ topics; число retries часто `3–5`. 
**RabbitMQ:** DLX/DLQ + TTL для отложенного retry. 
**NATS JetStream:** `AckWait` + `MaxDeliver`, например `AckWait=30s`, `MaxDeliver=5`; после превышения лимита приложение может отправить сообщение в error/DLQ subject.
## 6. Scaling
**Kafka:** добавляешь brokers при нехватке CPU/disk/network; consumer parallelism увеличивается количеством partitions. Если topic имеет `10 partitions`, одна consumer group эффективно может иметь максимум около `10` одновременно работающих consumers.  
**RabbitMQ:** чаще сначала добавляют consumers; если bottleneck сам broker — добавляют nodes/разносят queues.  
**NATS:** добавляешь server nodes; для JetStream контролируешь replicas и размещение streams, consumers масштабируешь под backlog.
## 7. Backup / Disaster Recovery
**Kafka:** replication защищает от падения broker, но не от случайного удаления данных; для критичных систем используют replication в другой cluster/region. **RabbitMQ:** backup definitions/users/vhosts/policies + стратегия восстановления сообщений. **NATS JetStream:** replicas + stream snapshots/backups. Обязательно проверять restore.
