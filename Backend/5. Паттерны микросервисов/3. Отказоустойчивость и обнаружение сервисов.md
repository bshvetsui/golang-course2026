## Отказоустойчивость
### 1. Retry

**Retry** — повтор запроса после временной ошибки.
`order-service → payment-service ❌ → retry → payment-service ✅`

Пример: Go-сервис получил `timeout/503` и повторяет запрос 2–3 раза. Обычно используют `exponential backoff`: `100ms → 200ms → 400ms`.
Важно: retry подходит для **временных ошибок**, а не для `400/401/404`. Для операций записи нужна **идемпотентность**, иначе повтор может создать два заказа или два платежа.
### 2. Circuit Breaker
**Circuit Breaker** — перестаёт слать запросы в сервис, который постоянно падает.
`Go service → Circuit Breaker → payment-service`

Состояния:
1. `Closed` — запросы идут нормально.
2. `Open` — сервис сломан, запросы сразу отклоняются.
3. `Half-Open` — через время отправляется тестовый запрос; если успешно → `Closed`.

Зачем: если PostgreSQL/payment-service лежит, не создавать тысячи бесполезных запросов и не положить остальные сервисы.
### 3. Bulkhead

**Bulkhead** — разделение ресурсов на независимые части, чтобы падение одной зависимости не забрало все ресурсы сервиса.

Например в Go:  
`payment requests → pool 50 goroutines`  
`notification requests → pool 20 goroutines`

Если `payment-service` завис и занял все свои 50 worker'ов, работа с Kafka/PostgreSQL и другими сервисами продолжится.
## Обнаружение микросервисов
**Service Discovery** — способ узнать, **по какому адресу сейчас находится нужный сервис**.

В Kubernetes Pod'ы постоянно создаются/умирают и получают новые IP, поэтому обращаться к конкретному IP нельзя.
### 4. Client-side Discovery
Клиент сам получает список доступных инстансов и выбирает один.

`order-service → Service Registry → payment-service-1/2/3`

Go-приложение получает адреса сервисов из Consul/Eureka и само делает load balancing.
### 5. Server-side Discovery
Клиент обращается к стабильному адресу, а инфраструктура сама выбирает нужный instance.

`order-service → Kubernetes Service → payment Pod`

Для Kubernetes это основной вариант:
`http://payment-service:8080`
Go-приложению не важно, какой конкретно Pod обработает запрос.
### 6. Sidecar Pattern
**Sidecar** — дополнительный контейнер рядом с приложением в одном Pod.
`Pod: [Go application] + [Envoy proxy]`

Go-приложение отправляет обычный HTTP/gRPC-запрос → Sidecar может сделать discovery, load balancing, retries, mTLS и tracing.
Именно так часто работает **Service Mesh**:

`Go → Envoy Sidecar → Envoy Sidecar → Go`
